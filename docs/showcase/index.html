    The assignment

    Four questions about open orders

    ACME Delivery Services wants its logistics leaders to follow their orders with low latency. The assignment supplied the orders database and its Debezium connector; I built the streaming pipeline and the model that answer these questions.

    1. Open orders by delivery date and status
    2. The top 3 delivery dates by open orders
    3. Pending items by product
    4. The top 3 customers by pending orders
    Decisions

    Why it is built this way

    The main choices I made. Open one for the reason and the alternative; each links to its full entry.

    D8Fully local, no cloud services

    The assignment asks for a stack reviewers can start from the README, so everything runs in Docker Compose on one machine. Managed AWS services would be closer to production, but need accounts and cost money.

    Read D8 →
    D29The source database and connector stay as provided

    I treated the database and the Debezium connector as given input. Bronze decodes their formats instead of changing the connector settings.

    Read D29 →
    D13SeaweedFS instead of MinIO

    MinIO is no longer maintained and its images can no longer be pulled. SeaweedFS is maintained, Apache-2.0 licensed and runs as one container with an S3 API. I also looked at a MinIO fork, RustFS and Garage.

    Read D13 →
    D9Iceberg with a JDBC catalog

    Iceberg is the table format; keeping its catalog in the analytics PostgreSQL avoids running another service. A REST catalog would be closer to production, at the cost of one more service.

    Read D9 →
    D27One driver container per application

    Each Spark job gets its own driver container, so a failure, its memory and its logs belong to one job only. In production this becomes YARN cluster mode on EMR, or Kubernetes.

    Read D27 →
    D17Landing, bronze, silver; gold built from silver

    Each layer has one job. Spark cannot stream from an Iceberg table that is updated in place, so an append-only silver keeps gold streamable. The cost is four hops, each adding some latency.

    Read D17 →
    D18Landing as raw Avro files

    An exact, replayable copy of Kafka, in a compact format that describes itself. The cost is one more hop before the data is typed.

    Read D18 →
    D30A readable change identity

    A change is identified by its key, its position in the source log and its operation, not by its Kafka offset, because the same change can arrive again at a new offset. Data Vault hash keys would work too, but are opaque.

    Read D30 →
    D31Late arrivals are history

    A late change takes its place in the history and never overwrites newer state. Bronze stays a faithful log; duplicates are removed in silver.

    Read D31 →
    D36How silver removes duplicates

    Exact duplicates are dropped when silver is written; versions that change nothing are folded when it is read. There is no time cut-off, so a late change is never dropped.

    Read D36 →
    D3Gold in PostgreSQL, not ClickHouse

    Gold is small and must be consistent after every micro-batch, and PostgreSQL applies each batch in one transaction. ClickHouse would handle much larger facts better, so it stays an option for scale.

    Read D3 →
    D32The gold dimensional model

    Customer and product dimensions with history, history facts and current-state tables answer every question. Current state as a plain view would get slower as the history grows.

    Read D32 →
    D35Public views over an internal schema

    The pipeline writes its own internal tables; consumers read views without the pipeline's columns. I can change how gold is stored without breaking the API or the dashboard.

    Read D35 →
    D40Indexes chosen from the query plans

    Gold has only the indexes the four questions use, each one picked by reading that question's query plan. Indexing every column would slow down every merge for no gain.

    Read D40 →
    D37Retention by monthly partitions

    PostgreSQL keeps 36 months of history by dropping whole months, which is cheaper than deleting rows. Current state is never trimmed, so an old open order keeps its row.

    Read D37 →
    D38Rebuild gold from silver

    Gold can be reset and rebuilt from silver with the same merge the stream uses, optionally up to a point in time. A separate batch loader would be a second copy of the rules to keep in step.

    Read D38 →
    D39Gold in the lake as views over silver

    Silver already holds every version, so the lake gets the gold model as views instead of a second writer. The cost is that every read recomputes over the full history.

    Read D39 →

    Run it

    From clone to answers in four commands

    You need Docker with Compose v2, GNU Make and uv. From the repository root:

    1

    Start the stack and every streaming job

    make pipeline PIPELINE=all
    2

    Check each layer against the one before it

    make data-quality
    3

    Ask a question

    curl -s localhost:8000/metrics/top-customers-by-pending-orders

    The dashboard is at localhost:3000/d/gold-metrics.

    4

    Stop everything, keeping the data

    make down

    The README quick start has every step.

    Production

    What production would need

    The pipeline logic, the model and the checks are built as they would be in production. The platform around them is simplified for one machine.

    • AWS S3 and a catalog service instead of SeaweedFS and the JDBC catalog.
    • Managed, replicated Kafka with more partitions and a schema registry.
    • Spark on EMR or Kubernetes, sized from measured streaming metrics.
    • Metrics, dashboards and alerts, and a data quality framework that keeps its results.
    • Secrets, TLS and authentication, infrastructure as code and deployments from CI.

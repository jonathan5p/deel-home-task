Deel data engineering take-home

Every change in a live orders database, streamed through a lakehouse into a star schema.

A change data capture pipeline built with open-source tools only. Debezium streams the supplied finance_db PostgreSQL through Kafka; Spark Structured Streaming lands, types and versions every change in an Iceberg lake on SeaweedFS, and keeps a star schema up to date in a separate PostgreSQL. Four business questions are answered by gold views, over an HTTP API and a Grafana dashboard. Everything runs locally with Docker Compose.

1 · The problem

Turn an operational database into near-real-time analytics

The assignment supplies a live PostgreSQL database, finance_db, whose operations schema holds customers, products, orders and order items. A data generator keeps changing it, and a Debezium connector already streams every change to four Kafka topics. The task is the analytical side: a Spark Structured Streaming application whose output answers the logistics team's questions with near-real-time updates.

The four business questions

  1. Number of open orders by delivery date and status
  2. Top 3 delivery dates with more open orders
  3. Number of open pending items by product
  4. Top 3 customers with more pending orders

What the solution had to deliver

Process the Debezium change events as a stream with Spark Structured Streaming.
Keep both the history and the current state of every order.
A consistent dimensional model that answers the questions.
Data ready to consume as soon as possible, served to stakeholders (API, dashboard or CLI).
An architecture diagram, a Spark sizing strategy with its variables, and evidence of the application running.

Constraints chosen

Fully local and open source: the whole stack runs in Docker Compose on one machine, so a reviewer can start it from the README (D8).

Source left as provided

The source DDL and the Debezium connector are used exactly as supplied; the pipeline handles their format, such as Debezium's variable-scale decimals and epoch timestamps (D29).

What "open" means

An open order is any order whose current status is not COMPLETED. Pending orders are the open orders, and pending items are the items of open orders. Both top-3 questions keep ties (D32).

2 · The solution at a glance

A medallion lakehouse with a dimensional model for serving

Each layer is its own streaming query with its own checkpoint, so every hop restarts where it stopped and never skips or repeats data. The lake keeps every change; PostgreSQL keeps what is served.

Capture

Debezium → Kafka

Every insert, update and delete of the four tables, read from PostgreSQL's write-ahead log into one topic per table.

Landing

Raw Avro files

Each Kafka record stored unchanged, with its topic, partition and offset: the replay source for bronze.

Bronze

Typed change log

One Iceberg row per change event with its change metadata; invalid records go to a quarantine table instead of failing the job.

Silver

Version history

Duplicate deliveries dropped, late changes kept as history; _history and _current views on top.

Gold · PostgreSQL

Star schema

SCD2 dimensions, append-only history facts and current-state tables, merged in one transaction per micro-batch.

Gold · lake

Iceberg views over silver

The same public model computed at read time from silver, over the full history, with natural keys.

Serve

API, Grafana, SQL

FastAPI and a provisioned Grafana dashboard read the gold views with read-only logins; Spark SQL and DuckDB read the lake.

Operate

Quality, upkeep, recovery

Layer-to-layer data quality checks, lake maintenance with an expiry guard, gold retention, bronze replay and gold rebuild.

    4 · Key decisions

    Why it is built this way

    The main design decisions, each with the reason and the alternative weighed. The numbers are the project's decision log numbers; each card links to the full entry.

    D17

    Layered lake: landing, bronze, silver; gold built from silver

    Why
    Spark cannot stream from an Iceberg table that receives MERGE or deletes, so an append-only silver keeps gold streamable.
    Trade-off
    Four streaming hops, each with its own checkpoint and commit latency. A fast path from bronze to gold is the fallback if latency matters.
    Read D17
    D18

    Landing as raw Avro files, one folder per topic

    Why
    Avro is row-oriented, compact and self-describing; raw key and value bytes stay valid if the topics move to a schema registry; Kafka coordinates make replays and gap checks possible.
    Trade-off
    One more hop before typed data, in exchange for a faithful, replayable copy.
    Read D18
    D30

    Change identity in readable columns

    Why
    A change is the entity key + _commit_sequence (the source LSN) + _change_op. Debezium re-sends a change at a new offset after a restart, so Kafka coordinates are lineage, not identity. _content_hash works like Data Vault's hash diff.
    Alternative
    Full Data Vault hash keys: they deduplicate as well, but give opaque ids for little gain with single integer keys.
    Read D30
    D31

    Late arrivals are history; deduplication happens in silver

    Why
    Bronze stays a faithful log. Silver drops repeated deliveries and appends a late change as history, where its validity range lands in place. Gold's current state only applies newer versions.
    Guard
    Lake maintenance never expires a snapshot a downstream stream still needs.
    Read D31
    D36

    Silver dedup: exact duplicates on write, unchanged versions on read

    Why
    dropDuplicates on the change identity with RocksDB state and no watermark: a redelivered change is appended once, a late change is never dropped. Views fold versions that change nothing.
    Alternative
    Python transformWithState (extra executor dependencies, every state call crosses to the JVM) or a per-batch lookup of silver.
    Read D36
    D3

    Gold in PostgreSQL, not ClickHouse

    Why
    Gold is small (current state, bounded history, dimensions) and must be consistent: PostgreSQL applies each micro-batch in one transaction, while ClickHouse's CDC tables deduplicate only eventually.
    Alternative
    ClickHouse fits billions of fact rows and scans over the full history better; it stays a candidate for scale.
    Read D3
    D32

    The gold dimensional model

    Why
    SCD2 customer and product dimensions, append-only history facts partitioned by month, and current-state tables that only take newer versions, with soft deletes so a late event cannot revive a row.
    Alternative
    Current state as a view or materialized view: slower as history grows, refreshed in full, and it loses old open orders once retention trims history.
    Read D32
    D35

    Public views over an internal schema

    Why
    The pipeline writes gold_internal; consumers read views of the same names in gold, without pipeline metadata or soft-deleted rows. The storage contract stays apart from the consumer contract.
    Trade-off
    One more layer of views to keep described and tested.
    Read D35
    D39

    Gold in the lake as Iceberg views over silver

    Why
    Silver already stores every version, so the lake keeps no copy: views apply gold's rules at read time, with natural keys. The gold job writes PostgreSQL only.
    Alternative
    A second MERGE-maintained Iceberg sink, or mirroring PostgreSQL into the lake. Cost: lake reads recompute over the full history.
    Read D39
    D40

    Gold indexes chosen from query plans

    Why
    Indexes exist only for the current use cases, each picked by reading that query's EXPLAIN plan: is_open stored on current_orders and partial indexes on the open orders.
    Result
    Pending items by product went from 344–380 ms to 37–46 ms on a 1M-order scratch database.
    Read D40
    D37 · D38

    Retention by monthly partitions; rebuild from silver

    Why
    History facts keep 36 months by dropping whole monthly partitions. Gold can be reset and rebuilt from silver, optionally up to a cutoff, through the stream's own merge.
    Alternative
    Row DELETEs for retention. A rebuild regenerates the surrogate keys.
    Read D37
    D13

    SeaweedFS instead of MinIO

    Why
    MinIO's repository is archived and its official images can no longer be pulled. SeaweedFS is actively maintained, Apache-2.0 licensed and runs as one container with an S3 API.
    Alternatives
    The pgsty/minio fork, RustFS, Garage.
    Read D13
    D9

    Iceberg with a JDBC catalog on the analytics PostgreSQL

    Why
    Iceberg is the table format of the target stack, and the JDBC catalog avoids running another service. A read-only REST catalog over it is optional, for engines such as DuckDB.
    Alternatives
    A REST catalog as the primary catalog (closer to production, one more service), or Delta Lake.
    Read D9
    D27

    One driver container per application

    Why
    A driver failure, its memory, logs and UI port belong to one application only. Standalone cluster mode does not support Python, so client mode in a per-run container is the closest local equivalent of a driver pod.
    In production
    EMR in YARN cluster mode, or the Spark Operator on Kubernetes.
    Read D27
    D29

    Source and connector stay as provided

    Why
    The assignment treats the source side as given. Bronze decodes Debezium's variable-scale decimal and epoch timestamps instead of changing the connector.
    Recommendation
    To the source owners: decimal.handling.mode=string and a publication limited to the four tables.
    Read D29
    5 · Quality and reliability

    Exactly once, checked at every boundary

    Every hop is restart-safe and idempotent, a chain of data quality checks compares each layer with the one before it, and the operations that touch data outside the stream are built so the stream never notices.

    Data quality chain

    Kafka→ landing → Landing→ bronze → Bronze + quarantine→ silver → Silver→ gold → PostgreSQL gold

    landing

    Every Kafka offset landed exactly once, contiguous against the offsets Kafka actually holds, with the same bytes as Kafka.

    bronze

    Every landed record is in bronze or in quarantine, never both and never twice, and each table holds only records of files its own query committed.

    silver

    Silver holds every change identity bronze held at the snapshot silver read up to, once, and no other.

    gold

    Each PostgreSQL gold view equals its lake view computed over silver at the snapshots gold committed, so silver, gold and the lake views are checked in one pass.

    Each check is bounded by what the downstream query has committed, so results do not depend on pipeline lag. make data-quality runs them as their own Spark application, writes a JSON report to the lake and exits 1 on any failure; the data-quality profile runs them on a schedule. Data quality checks

    Exactly once, hop by hop

    HopWhat makes a restart or replay safe
    Kafka → landingSpark's file sink records committed files in _spark_metadata, and the checkpoint records the offsets. Readers see committed files only.
    Landing → bronzeThe checkpoint records the landing files processed; Iceberg's streaming sink stores the query and batch id in each snapshot and skips a batch it already committed.
    Bronze → silverdropDuplicates on (key, _commit_sequence, _change_op) with RocksDB state saved in the checkpoint, so a change seen before a restart is still dropped after it.
    Silver → goldStaging is replaced, history inserts use ON CONFLICT DO NOTHING, current state only takes a higher _commit_sequence. PostgreSQL commits before the checkpoint, so a batch replayed after a crash merges to the same rows.
    Concurrency in goldEvery merge takes one advisory lock, so a fact merge and a dimension merge never miss each other's uncommitted rows. Staging runs outside the lock, in parallel.

    Late arrivals: try it

    Order 7's changes arrive out of order. History keeps every change in _commit_sequence order; current state only moves forward. The example is the one in the gold model's versioning rules.

    gold.fact_order_history (order 7)

    _commit_sequencestatusvalid until

    gold.current_orders (order 7)

    status_commit_sequenceopen

    Apply the changes in the order they arrive.

    Lake maintenance and the expiry guard

    1. rewrite_data_files compacts the small streaming files into a replace snapshot, which Iceberg's streaming reader skips.
    2. Before expire_snapshots (7 days, last 10 kept), the guard reads every downstream stream's checkpoint and skips expiry for a table whose stream still needs a snapshot.
    3. remove_orphan_files deletes unreferenced files older than 3 days.
    4. The silver and lake gold views are refreshed, so a changed definition reaches the lake without a restart.

    7 · How to run it

    From clone to answers in four commands

    You need Docker with Compose v2, GNU Make and uv. The Spark workers alone can claim 10 GiB of executor memory, so give Docker enough memory for the whole stack.

    1

    Start the stack and every streaming job

    make pipeline PIPELINE=all

    Debezium snapshots the source tables, then streams every change; landing, bronze, silver and gold pick them up within a few 10-second micro-batches. Until a layer has data, the next job restarts with PATH_NOT_FOUND or TABLE_OR_VIEW_NOT_FOUND, which is expected.

    2

    Check the data, layer by layer

    make data-quality

    Ends with a DATA QUALITY summary and exits 1 if any check fails.

    3

    Ask the four questions

    curl -s localhost:8000/metrics/top-customers-by-pending-orders

    Or open the dashboard at http://localhost:3000/d/gold-metrics, the API docs at http://localhost:8000/docs, and the Spark master at http://localhost:8080.

    4

    Stop, keeping the data

    make down

    Volumes survive, so the source, Kafka, the lake and gold are still there after the next make pipeline. The README has every command, and Running the pipeline the details.

    8 · What production would need

    Same design, managed pieces

    The local layout mirrors a production deployment on one small, shared cluster. Moving it is mostly configuration and sizing, not a redesign.

    Compute

    • Each streaming job as its own application: EMR in YARN cluster mode, or a Spark Operator SparkApplication on Kubernetes.
    • Fixed executors per stream, sized from the streaming metrics; dynamic allocation for batch jobs.

    Storage and catalog

    • S3 instead of SeaweedFS, a configuration change.
    • A REST catalog or AWS Glue instead of the JDBC catalog.
    • Checkpoints and event logs on S3.

    Throughput

    • More Kafka partitions per topic; maxOffsetsPerTrigger to cap catch-up batches.
    • Silver's state partitions chosen ahead of growth.
    • Gold is bound by its single writer lock: longer triggers, finer locking, or a store built for larger facts.

    Observability

    • Streaming metrics in a time-series system instead of the Spark UI.
    • Per-batch stats in a separate observability catalog in the lake (proposed, D33).

    Data quality and upkeep

    • A data quality framework (such as Deequ, Great Expectations or Soda) for declarative checks, profiling, history and alerting.
    • Maintenance and retention submitted by a scheduler instead of Compose loops.

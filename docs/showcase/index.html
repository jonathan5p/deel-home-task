Deel data engineering take-home

A CDC pipeline, from the orders database to the answers

I built a pipeline that streams every change in an orders database through Kafka and Spark into an Iceberg lake, and into a star schema in PostgreSQL that answers four business questions.

Overview

From a commit to an answer

Debezium captures every change in the orders database. Spark carries it through the lake's layers and merges it into a star schema in PostgreSQL, which the API and Grafana read.

      Decisions

      Why it is built this way

      The main choices I made. Open one for the reason in a sentence or two, with a link to its full entry.

      Fully local, no cloud servicesD8

      Reviewers can start everything from the README, with Docker Compose on one machine. Managed AWS services would be closer to production, but need accounts and cost money.

      Read more: D8 →
      The source database and connector stay as providedD29

      I treated them as given input, so bronze decodes their formats instead of changing the connector settings.

      Read more: D29 →
      SeaweedFS instead of MinIOD13

      MinIO is no longer maintained and its images can no longer be pulled. SeaweedFS is maintained, Apache-2.0 licensed and one container with an S3 API.

      Read more: D13 →
      Iceberg with a JDBC catalogD9

      Keeping the catalog in the analytics PostgreSQL avoids running another service. A REST catalog would be closer to production.

      Read more: D9 →
      One driver container per applicationD27

      A failure, its memory and its logs belong to one job only. In production this becomes cluster mode on EMR or Kubernetes.

      Read more: D27 →
      Landing, bronze, silver; gold built from silverD17

      Each layer has one job, and an append-only silver lets gold read it as a stream. The cost is some latency per hop.

      Read more: D17 →
      Landing as raw Avro filesD18

      An exact, replayable copy of Kafka in a format that describes itself, at the cost of one more hop.

      Read more: D18 →
      A readable change identityD30

      A change is identified by its key, its position in the source log and its operation, not by its Kafka offset, because a redelivered change gets a new offset.

      Read more: D30 →
      Late arrivals are historyD31

      A late change takes its place in the history and never overwrites newer state. Bronze keeps everything; silver removes the duplicates.

      Read more: D31 →
      How silver removes duplicatesD36

      Exact duplicates are dropped on write and versions that change nothing are folded on read. There is no time cut-off, so a late change is never dropped.

      Read more: D36 →
      Gold in PostgreSQL, not ClickHouseD3

      Gold is small and must be consistent after every micro-batch, and PostgreSQL applies each batch in one transaction. ClickHouse stays an option for scale.

      Read more: D3 →
      The gold dimensional modelD32

      Dimensions with history, history facts and current-state tables answer every question. Current state is a table because a view over the history would get slower as it grows.

      Read more: D32 →
      Public views over an internal schemaD35

      Consumers read views without the pipeline's columns, so I can change how gold is stored without breaking the API or the dashboard.

      Read more: D35 →
      Indexes chosen from the query plansD40

      Only the indexes the four questions use, each picked from that question's query plan. More would slow down every merge for no gain.

      Read more: D40 →
      Retention by monthly partitionsD37

      PostgreSQL keeps 36 months of history by dropping whole months, which is cheaper than deleting rows. Current state is never trimmed.

      Read more: D37 →
      Rebuild gold from silverD38

      Gold is rebuilt with the same merge the stream uses, optionally up to a point in time, so there is no second copy of the rules to keep in step.

      Read more: D38 →
      Gold in the lake as views over silverD39

      Silver already holds every version, so the lake gets the gold model as views instead of a second writer. Every read recomputes over the full history.

      Read more: D39 →

      Run it

      From a fresh clone to the answers

      You need Docker with Compose v2, GNU Make and uv.

      1

      Clone the repository

      git clone https://github.com/jonathan5p/deel-home-task.git && cd deel-home-task
      2

      Start the stack (source and CDC, the lake, Spark, the analytics database, the API and Grafana)

      make up
      3

      Start the streaming jobs (this would also start the stack on its own)

      make pipeline PIPELINE=all
      4

      Check every layer against the one before it

      make data-quality
      5

      Ask a question

      curl -s localhost:8000/metrics/top-customers-by-pending-orders

      The dashboard is at localhost:3000/d/gold-metrics.

      6

      Stop everything, keeping the data

      make down

      Production

      What production would need

      The pipeline logic, the model and the checks are built as they would be in production. The platform around them is simplified for one machine.

      • AWS S3 and a catalog service instead of SeaweedFS and the JDBC catalog.
      • Managed, replicated Kafka with more partitions and a schema registry.
      • Spark on EMR or Kubernetes, sized from measured streaming metrics.
      • Kafka and PostgreSQL metrics next to Spark's, alerts that notify someone, and a data quality framework that keeps its results.
      • Secrets, TLS and authentication, infrastructure as code and deployments from CI.

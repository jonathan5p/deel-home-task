# Notes for the M7 docs revamp

Material removed from code during review, to fold into the M7 documentation (#169, #130). Local only. Agents add notes here only when the user asks; whether a removed explanation belongs here is the user's call.

## Gold business views and indexes (removed from #142)

- `is_open` is stored with the order on `current_orders` so the planner can see how few orders are open; it cannot see that through a join to `dim_order_status`. Partial indexes on open orders keep only those rows, with the columns the business views read.
- `gold.open_orders` is the one definition of an open order. The partial indexes on `current_orders` use the same predicate, so the business views that read this view can use them.
- A view keeps no row order, so consumers add the `ORDER BY` they need, as the queries in `analytics/sql/gold/` do.
- `RANK` gives tied rows the same place and skips the places after them, so every row tied for third is kept and no more than three places are reported. The same holds for top customers.
- `top_customers_by_pending_orders` left-joins `dim_customer`, so a customer that is not in `dim_customer` yet still appears, with a null name.

## Read-only access and the API (removed from #158, #162, #164)

- Consumers log in with a service login of their own that is a member of the NOLOGIN `gold_reader` role (`docker/analytics-db/initdb/03-service-logins.sh`). The `gold` views run with their owner's rights, so reading them needs no access to `gold_internal`. The grants come last in the DDL so they cover every view, and dropping the gold schema drops them, which is why they live in the DDL.
- `03-service-logins.sh` runs after the gold DDL on an empty volume, and again with `make db-logins` on an existing one, so every statement must be safe to repeat. `create_login <login> <password> <statement timeout>`.
- Infra tests connect as the service login over TCP so its password is checked (the local socket is trusted).
- The API pool checks each connection before handing it out, so one broken by a database restart is replaced instead of failing a request. The pool opens without waiting, so the API starts, and reports itself unhealthy, while the database is down, and keeps reconnecting in the background.
- Unexpected errors return a generic 500; Starlette re-raises after the handler, so the server still logs the traceback. `RepositoryUnavailableError` messages are safe to show clients (503).
- Each metric query orders rows like its `analytics/sql/gold/` query. Gold stores source commit times as UTC timestamps without a zone; the freshness query left-joins a clock row so it answers even when the view is empty. Freshness lag grows while the source is idle, even when the pipeline is healthy.
- The API image needs every workspace member's `pyproject.toml` for uv, even for members it does not install.

## Silver → gold quality check (removed from #46)

- The check compares each gold public view with silver's own `_history`/`_current` SQL run over a silver snapshot, so the fold rule and validity ranges are silver's, not recomputed. Gold-only columns (surrogate keys, looked-up values) are not compared.
- `_changed_at` on the current views is not compared: gold's current row is the latest change, folded or not, while silver's current version starts at the first of the repeats.
- Gold views never show a delete as current; silver's history view does, so those rows are filtered.
- PostgreSQL commits a micro-batch before Spark records it in `commits/`, so gold can be one batch ahead of the last committed one. Gold is read once, between reading the last committed batch and the newest batch started after it; the view passes if it matches either snapshot, otherwise it is reported against the committed one.
- PostgreSQL's unconstrained `numeric` reaches Spark through JDBC with a different decimal type, so values are aligned before comparing.

## Gold retention and rebuild (removed from #149, #150)

- `ensure_history_partitions` moves rows the default partition already holds for a new month into it, because PostgreSQL cannot add a partition while the default partition holds rows in its range. Every month the default partition holds gets its own partition, so retention can drop it whole.
- `apply_history_retention` drops a month only when it ends before the window starts, so at least `keep_months` full months are always kept. The upper bound is read from the partition itself, not its name.
- Retention runs as an optional Compose service every `GOLD_RETENTION_INTERVAL_HOURS` (default 24); a failed run waits for the next. Applying the DDL creates no monthly partitions.
- Rebuild loads every silver change up to `to_time` through the gold job's own sinks, one batch per load, dimensions first so facts resolve against complete dimensions (the merges re-resolve each other, so order changes no result), then applies retention.
- Surrogate keys are regenerated by a rebuild, so rebuilt and streamed gold are compared by business key and `_commit_sequence`.
- Grafana and API infra tests commit their fixture rows because the service queries in its own session and would never see rows a test rolls back.

## Gold in the lake (removed from #152, #154)

- The lake gold views are the public gold relations computed at read time from silver, with natural keys instead of PostgreSQL's generated surrogate keys. Folding and validity come from silver's history views; the gold views add key lookups (seeded dimensions joined on their code), as-of dimension attributes and current state, from the same declarations the PostgreSQL writer uses.
- Dimension views leave deletes out: the version before a delete ends with it and is not current. Fact history views fold unchanged changes; a delete is the last change and never current. Current views take the latest change of every non-deleted key from the silver table, folded or not, which is what PostgreSQL's current state holds.
- `line_amount`: `DECIMAL(27, 10)` times an int fits `DECIMAL(38, 10)` exactly; at the lake's `DECIMAL(38, 10)` inputs Spark would round the product to 6 decimals.
- The gold-lake check compares each lake view with its PostgreSQL view as multisets, at the silver snapshots of each gold stream's last committed batch and of the batch in flight (PostgreSQL may already hold a batch its checkpoint hasn't committed). PostgreSQL rows are cast to the lake's types (JDBC reads decimals differently). Surrogate keys are mapped to the dimension version's `_commit_sequence`. Fact history is compared only from the first month PostgreSQL still holds, so both sides fold the same rows after retention. Freshness is not compared (one time per entity, not rows). Stale stored views fail the check.

## Lake maintenance (removed from #135)

- A stream restarts from the snapshot of its last committed batch, so expiry must keep it: it is lost when it is older than the cutoff and not among the `retain_last` newest snapshots, or already gone. The guard reads each downstream checkpoint: a batch is committed once `commits/<batch>` exists, and its `offsets/<batch>` file holds a version line, a metadata line, then one offset per source; Iceberg's offset names a `snapshot_id`. Checkpoints are read through Spark's Hadoop file systems, so `s3a://` and `file://` both work.
- The default downstream covers silver's streams on bronze and gold's four streams on silver (customers, products, orders, order items).
- Every expired snapshot takes its manifest list with it. Iceberg refuses to remove orphan files younger than a minimum age, because a running write may still add them. Orphan listing uses the table's FileIO prefix listing, because Hadoop's file systems cannot list the warehouse's `s3://` paths.
- The job maintains every table, then fails if any table failed, so one broken table never blocks the others. It runs as an optional Compose service every `MAINTENANCE_INTERVAL_HOURS` (default 24); a failed run waits for the next.

## Recovery operations (for the report)

| | Bronze replay (#133) | Gold rebuild (#150) |
|---|---|---|
| Purpose | Fill gaps: re-read a landing range and append only the changes bronze lacks | Recreate gold from scratch from silver |
| Destructive | No, append-only | Yes: `gold-reset` drops and recreates the gold schemas and checkpoints |
| Input | Landing topic + offsets or time range | All of silver, optionally up to `TO_TIME` |
| Dedup | Anti-join on (key, `_commit_sequence`, `_change_op`); quarantine once per source coordinates | Starts empty; loads through the gold job's own sinks |
| Afterwards | Silver picks the rows up as late events; no restart | Gold job left stopped; `make pipeline` resumes from fresh checkpoints |
| Side effects | None | Surrogate keys regenerated |
| When | Missed or failed range | Logic or schema change in gold, corrupted gold |

Both reuse the streaming code (`parse_changes`, the gold `MergeSink`) and are tested to equal streaming output. Full bronze rebuild is a manual README procedure. Possible extension: a "replay a silver range into gold" job, cheap because the gold writer is idempotent (`ON CONFLICT DO NOTHING` plus newer-only `MERGE`).

## Gold writer (removed from #141)

- Every gold merge takes the writer lock first, so gold writers commit one at a time. A fact merge resolves its dimension keys from the committed dimension rows, and a dimension merge re-resolves the committed fact rows. Run side by side, each would miss the other's uncommitted rows and leave a fact pointing at the wrong dimension version. `gold-model.md` covers this under "One writer at a time".
- The writer's SQL is built from schema identifiers, never from data, so it needs no query parameters.
- Loading approach per micro-batch: Spark JDBC overwrites an unlogged staging table outside the lock, then one PostgreSQL transaction under the lock inserts new versions, merges current state and re-resolves facts. Tracked in #169.

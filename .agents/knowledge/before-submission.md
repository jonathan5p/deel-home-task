# Before submitting the home task

Personal checklist to go through before sending the take-home. Agents: remind the user of the open items whenever submission, the final README, or M7 (architecture, sizing, evidence) comes up.

- [ ] **Study `docker/spark/spark-defaults.conf`** (added 2026-11-05 in PR #73). Be able to explain each line in the interview:
  - `spark.eventLog.enabled` / `spark.eventLog.dir`: every driver writes its event log to the shared `spark-events` volume, whether or not the history server is running.
  - `spark.eventLog.rolling.enabled` / `spark.eventLog.rolling.maxFileSize 128m`: long-running streaming drivers write the log in bounded files instead of one ever-growing file. Know what the history server does with rolled files and what compaction (`spark.history.fs.eventLog.rolling.maxFilesToRetain`) would add.
  - `spark.history.fs.logDirectory`: where the history server reads from; it must match `spark.eventLog.dir`.
  - Why the file is baked into the image (one image for master, workers, driver and history server), and how a `--conf` on `spark-submit` or a `SparkSession.builder.config` overrides it (precedence: code > `--conf` > `spark-defaults.conf`).
  - What would change in production: event logs on object storage (SeaweedFS/S3) instead of a local volume, retention and cleaner settings (`spark.history.fs.cleaner.*`).

## Must appear in the final report (M7)

- [ ] **Gold model definitions** (decision D32): open order = status other than COMPLETED, pending orders = open orders, pending items reported as count and quantity, top 3 includes ties, current-state tables with newer-version-only upserts.
- [ ] **Gold public views** (decision D35): consumers read `gold` views without pipeline metadata (`_commit_sequence`, soft deletes); the pipeline writes `gold_internal` tables.
- [ ] **Observability catalog** (decision D33): pipeline metrics live in a separate `observability` catalog in the lake, apart from business data.
- [ ] **Late arrivals and deduplication** (decision D31): bronze as a faithful log, silver deduplicating by change identity, late versions appended as history with `valid_to` derived in views, gold applying only newer versions.
- [ ] **Bronze change identity and neutral names** (decision D30): readable change identity, `content_hash` from Data Vault's hash diff for re-snapshots and audit-only updates, neutral metadata names, and why full Data Vault hashing was not adopted.
- [ ] **Source side left as provided** (decision D29): Spark decodes Debezium's variable-scale decimal instead of changing the connector; recommend `decimal.handling.mode=string` and a publication limited to the four tables (#84) to the source owners.

- [ ] **Object store: MinIO → SeaweedFS** (decision D13). The original idea was MinIO. It is no longer maintained (repository archived, last release October 2025, official images no longer pullable), so maintained open-source S3-compatible options were evaluated: SeaweedFS, the `pgsty/minio` community fork, RustFS and Garage. SeaweedFS was chosen (Apache-2.0, actively maintained, one all-in-one container, S3 API). Note that any S3-compatible store or AWS S3 is a configuration change.
- [ ] **How the gold PostgreSQL indexes were chosen** (decision D40; #142, #45; written up in #167 `decisions.md` and #161 `sizing.md`): indexes were picked from the current use cases only, the four business questions and the `gold.open_orders` view, by reading each query's EXPLAIN plan. Partial indexes on `current_orders` (`WHERE is_open AND NOT _is_deleted`) turn the delivery-date and top-customer views into index-only scans, and storing `is_open` on `current_orders` lets pending items use an `(order_id)` index. Four earlier current-state indexes no plan used were dropped. Include a with/without-index timing table per query (#142's PR body has the first numbers, e.g. pending items 344–380 ms → 37–46 ms on 1M orders / 3M items), ideally re-measured on the real run in #58, and say that new use cases would get new indexes the same way.
- [ ] **Recovery operations: bronze replay vs gold rebuild** (#133, #150): replay is additive (re-reads a landing range by offsets or time, appends only changes bronze lacks by key + `_commit_sequence` + `_change_op`, quarantines failures once per source coordinates; silver sees the rows as late events, no restart). Gold rebuild is destructive (`gold-reset`, then a batch load of all silver up to `TO_TIME` through the gold job's own sinks, dimensions first, then retention; gold job left stopped; surrogate keys regenerated). Both reuse the streaming code so they match streaming output (tested). Full bronze rebuild is a manual README procedure. Mention that a "replay a silver range into gold" job would be cheap because the gold writer is idempotent, as a possible extension. Include a when-to-use table (missed range vs logic/schema change or corruption).
- [ ] **Data quality: custom checks here, a framework in production** (#145 chain, #151, #154, #179, #180, #181): this project builds its own layer-to-layer checks (`pipelines/quality/`, `make data-quality`, JSON reports in the lake) to keep the stack small and show the reconciliation logic. In a real project, use a specialised data-quality framework instead, such as AWS Deequ (or PyDeequ) on Spark, Great Expectations or Soda, for declarative checks, profiling, anomaly detection, result history and alerting. Link #112 (M8, evaluate a data quality framework) and #116 (persist results).
- [ ] **Lake maintenance in production** (#135 review): the local `maintenance-job` is a Compose shell loop. In a real deployment it would be either a job inside the EMR/Databricks cluster (e.g. a scheduled Databricks job or EMR step) or a separate scheduler/service (Airflow, a cron service, EventBridge) that submits the Spark job on a schedule.
- [ ] **Driver placement vs EMR/Kubernetes** (decision D27): per-run driver containers in client mode with shared standalone workers; contrast with YARN cluster mode / EMR Serverless / Spark Operator driver and executor pods, and the core-cap (`spark.cores.max`) sizing consequence.
